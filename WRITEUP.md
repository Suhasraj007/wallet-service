# Write-up — Wallet / P2P Transfer Service

## Data model

Two tables. `wallets(user_id PK, balance_paise BIGINT CHECK >= 0)` — the primary key is the entire get-or-create story. `transfers(id, from_user, to_user, amount_paise CHECK > 0, idempotency_key, request_hash, status, from_balance_after, UNIQUE (from_user, idempotency_key), CHECK from_user <> to_user)` — the ledger: one row per attempt, holding its final outcome. `from_balance_after` stores the original response so a replay is byte-identical. Money is integer paise end to end (BIGINT / Java `long`); the CHECK constraints are a last line of defence no code path can bypass.

## The get-or-create + transfer mechanism

One transaction, four steps, in a proven order: (1) `INSERT ... ON CONFLICT (user_id) DO NOTHING` for both wallets, in sorted user-id order — the unique index makes creation exactly-once with no exception, so the classic SELECT-then-INSERT race that 500s cannot exist. (2) `SELECT ... FOR UPDATE` on both rows, again sorted — one global lock order, so crossed concurrent transfers (A→B and B→A) cannot deadlock. (3) Insert the transfer row; its unique key is the idempotency arbiter. (4) Check funds, then apply both balance updates or record the rejection; commit.

The order is measured, not stylistic. Inserting the transfer row before locking makes its foreign keys take KEY SHARE locks on both wallet rows, so the later `FOR UPDATE` becomes a lock upgrade across transactions: under a 40-way concurrent burst, 38 of 40 requests deadlocked — each one would be an HTTP 500. Locks-first eliminates the upgrade: the FK check happens under locks the transaction already holds. Rejected heavier alternatives: SERIALIZABLE isolation with retry loops (more code, and retry storms under exactly the burst being tested), Postgres advisory locks (a second lock namespace whose ordering must also be got right), Redis/distributed locks (new infrastructure and fencing problems when the database is already the serialization point), and per-pair queues (operational complexity, no added correctness).

## Idempotency: where the key lives, matching, expiry

The key lives on the transfer row itself, scoped per caller — `UNIQUE (from_user, idempotency_key)` — with a SHA-256 hash of the body (`to_user|amount_paise`). It sits inside the same transaction as the money movement, after the row locks and before the balance mutation, so "key taken" and "money moved" commit together and can never disagree. Concurrent same-key twins serialize on the sender's row lock; the loser's insert returns no row, it rolls back and serves the winner's committed outcome; a lock-free committed-read fast path answers later retries. Matching: same key + same hash → the stored original outcome, status code included (a replayed rejection returns the same 422). Same key + different hash → 409. Expiry: never — the transfer row is the ledger, and any TTL window re-opens double-apply exactly when a very late retry arrives. Rejections consume keys too: a key names one attempt and its one outcome; retrying after topping up is a new attempt, so a new key.

## Identity and authorization

HS256 JWT (jjwt); the secret comes from the environment and the app refuses to start if it is under 32 bytes. A small explicit servlet filter (~40 lines) verifies signature, issuer and expiry, and injects the subject; controllers receive the caller only through a `@Caller` parameter — no code path reads the payer from a header or body field. `/auth/token` is a deliberately minimal stand-in for a real identity provider so evaluators can mint brand-new users. Transfers are readable only by participants, and non-participants get the same 404 as a missing id, so transfer ids leak nothing. One scheme and four protected routes made an auditable filter the right size over Spring Security; with multiple schemes or roles I would reach for the framework.

## Consistency vs availability (the CAP call)

For money, consistency wins — implemented, not asserted. Every database wait is bounded (10 s to acquire a pooled connection, 30 s socket read), so the transfer path fails closed instead of hanging; the API returns 503 with Retry-After, and the client retries with the same idempotency key — which is precisely what makes that retry safe. No write-behind queue or "accept now, apply later": that is how double-spends are born. Reads are uncached — a cached balance lies about spendable money, and the read load here does not justify one. `/readyz` performs a real `SELECT 1`, so an orchestrator stops routing before users see failures. Those limits are deliberately sized above legitimate contention rather than below it: concurrent transfers between one pair serialize on a single row lock by design, and that queueing must never be misread as a database fault and turned into a 5xx. NFR priority for the write path: correctness > availability > latency; availability is recovered through safe client retries, not server-side guessing.

## Edge cases

Insufficient funds → 422: the request is well-formed, but the wallet state cannot satisfy it — 400 would blame the request's shape, 409 is taken by key conflicts, and 402 is reserved with payment-scheme-specific semantics. Self-transfer → 422, backed by a DB CHECK. Unknown recipient is not an error — creating it atomically is the requirement. Replay vs conflict: stored original vs 409, as above. Zero or negative amounts → 400 via validation plus a DB CHECK. One honest gap in the brief: there is no deposit endpoint, so brand-new wallets are seeded with a configurable demo balance (`INITIAL_BALANCE_PAISE`, default ₹1,000) — otherwise no transfer could ever succeed. Conservation still holds exactly — the sum of balances always equals wallets created × seed — and the burst script asserts it to the paisa.

## Containerization, deployment, observability

Multi-stage Dockerfile → JRE-only image running as non-root uid 10001, with a container HEALTHCHECK on `/healthz`; `docker compose up --build` brings up app + Postgres in one command; all secrets via environment, nothing committed (12-factor). Deployed as a container image built from the Dockerfile (not a buildpack) on Render's free tier, backed by Neon free Postgres over TLS. Logs are structured JSON with a per-request correlation id (client `X-Request-Id` honoured or generated, echoed back), and every meaningful event is a named log with key-value fields: `transfer_applied`, `transfer_rejected_insufficient_funds`, `idempotent_replay`, `idempotency_conflict`, `wallet_created` (with `during=transfer` marking the get-or-create race path), `auth_failure`, `database_unavailable`. The same stream is pushed to Grafana Cloud Loki, and the public logs link is a Grafana shared dashboard. `GET /metrics` serves Prometheus text: request count and latency with p99 histograms, plus counters for applied/rejected transfers, replays, conflicts and auth failures.

## AI usage — directed vs decided

Directed: the proof-first workflow — I required an empirical concurrency experiment against real Postgres before any Java was written; that experiment is what exposed the FK lock-upgrade deadlock (the 38/40 number) and fixed the final statement order. I also directed the scope: smallest correct surface, a Testcontainers gate reproducing this exercise's probe, and the one-command burst script. Produced by the AI: the Spring implementation of the agreed design, the tests, and first drafts of the docs — every piece reviewed before keeping. Decided by me: the shipped mechanism (unique-index arbiter plus sorted row locks, over SERIALIZABLE, advisory locks or Redis), the idempotency policy (per-caller scope, no expiry, rejections consume keys), the 422/409/404 semantics, the seed-balance call, and the fail-closed stance. Overrode: an early draft mapped a dead database to 500; I required 503 + Retry-After to match the stated NFR.
